# PA4 — события и подписчики

Лабораторная выполнена в ветке `pa4` поверх `pa3`.
Требования: [PA4](https://github.com/tanyginvv/DISTRIBUTED-PROGRAMMING/tree/pa4).

## Архитектура

C4-диаграмма контейнеров записана в PlantUML: [architecture.puml](docs/architecture.puml).
Исходник использует библиотеку C4 из стандартной поставки PlantUML и включает
браузер, все сервисы, протоколы связей и число экземпляров.

Nginx распределяет HTTP-запросы между двумя Valuator. Два RankCalculator
конкурируют за задания из устойчивой очереди `rank-tasks`. Два EventsLogger
подписываются на обменник `text-events` типа **fanout**. У каждого логгера собственная
временная очередь, поэтому **каждый экземпляр получает оба типа событий**.
Схема подписки соответствует [примеру RabbitMQ для .NET](https://www.rabbitmq.com/tutorials/tutorial-three-dotnet).

1. POST сохраняет текст в Valkey (`TEXT-{id}`). Пустой ввод сохраняется как пустая строка.
2. Valuator вычисляет similarity через SHA-256 и атомарный `SET NX` по ключу
   `SEEN-{hash}`: первое появление текста даёт `0`, повторное — `1`.
   После записи `SIMILARITY-{id}` публикуется `SimilarityCalculated`.
3. Valuator отправляет задание `CalculateRank` в `rank-tasks` и возвращает **302**
   на `/summary?id=<uuid>` после подтверждения брокером обеих публикаций.
   При ошибке сохранения или публикации возвращается **503** с сообщением и сохранённым вводом.
4. RankCalculator читает текст, вычисляет rank и записывает `RANK-{id}`.
   Затем публикует `RankCalculated` и ждёт publisher confirm. Только после этого
   отправляет ack задания. Ручное подтверждение и `prefetch=1` распределяют работу между репликами.
5. Каждый EventsLogger читает собственную очередь и выводит `Type`, `TextId`,
   название метрики, её значение и `Instance`. Ack события отправляется после записи в журнал.
   Некорректный JSON, неизвестный тип или неверные данные отклоняются с записью ошибки.

Алгоритм rank сохранён из PA3: доля символов, не являющихся латинскими или
русскими буквами (включая `Ёё`), с подсчётом длины в UTF-16. Для пустого текста rank `0`.
На summary наличие записи определяется по исходному тексту. Если rank ещё нет,
показаны **«Оценка содержания не завершена»**, similarity и кнопка обновления.
Неизвестный или неверный ID — **«Запись не найдена.»**.

## Контракты и доставка

Все сообщения содержат JSON; свойство AMQP `Type` задаёт тип контракта:

| Type | JSON | Получатель |
| --- | --- | --- |
| `CalculateRank` | `{"TextId":"<uuid>"}` | Один из конкурирующих RankCalculator |
| `SimilarityCalculated` | `{"TextId":"<uuid>","Similarity":0}` | Каждый подключённый EventsLogger |
| `RankCalculated` | `{"TextId":"<uuid>","Rank":0.25}` | Каждый подключённый EventsLogger |

Издатели используют сохраняемые сообщения и publisher confirms. Параллельные
POST сериализуют работу общего канала RabbitMQ через `SemaphoreSlim`.
Для заданий применяется `mandatory=true`; для событий — `mandatory=false`,
поскольку отсутствие подписчиков допустимо.

Очередь `rank-tasks` устойчивая. Повторная обработка записывает тот же rank;
после сбоя публикации события неподтверждённое задание доставляется повторно.
При временной ошибке Valkey обработчик удерживает задание и повторяет операцию
через 2 секунды. Некорректные задания и ссылки на отсутствующий текст отклоняются без повторной постановки.

Обменник `text-events` устойчивый. Очереди подписчиков создаются с именем,
назначенным брокером, и параметрами `durable=false`, `exclusive=true`, `autoDelete=true`.
При отключении подписчика его очередь удаляется. После восстановления соединения
EventsLogger создаёт новую очередь и подписку. **Воспроизведение истории не предусмотрено**:
события за время отсутствия подписчика могут быть потеряны. Повторная доставка
заданий может привести к повторным событиям; порядок событий не гарантируется.

Publisher confirm подтверждает приём брокером, а не запись событий в журнал каждого логгера.
HTTP, Valkey и RabbitMQ не объединены транзакцией. При неудачной публикации
сохранённые данные или уже опубликованное событие могут остаться; повторный POST создаёт новый TextId.

## Запуск и масштабирование

Нужны Docker Engine и Docker Compose с поддержкой `scale`.
Перед переходом из PA3 остановите её Compose-проект. В корне ветки `pa4`:

```bash
docker compose up -d --build
docker compose logs -f
docker compose down
```

Приложение: http://localhost:8080. RabbitMQ Management: http://localhost:15672.
Учётные данные лабораторного брокера: `student` / `student`.
По умолчанию работают два Valuator, два RankCalculator и два EventsLogger.

```bash
docker compose up -d --scale valuator=3 --scale rankcalculator=3 --scale eventslogger=3
```

Nginx обновляет адреса Valuator через Docker DNS каждые 5 секунд, внешние порты
репликам не нужны. Экземпляр веб-приложения указан в `X-Valuator-Instance`.

Compose ждёт готовности Valkey и RabbitMQ перед запуском приложений.
Redis-клиент восстанавливает подключения автоматически, потребители RabbitMQ
повторяют подключение через 2 секунды. Издатель подключается заново при следующей публикации.
EventsLogger зависит только от RabbitMQ и не обращается к Valkey.

Общие тома: `dpkeys` для ключей ASP.NET Data Protection, `valkey-data` для AOF,
`rabbitmq-data` для данных брокера. Общие ключи позволяют получить форму в одной
реплике Valuator и отправить её в другую. `docker compose down` сохраняет тома.

## Самостоятельная проверка

Сборка, тесты и запуск Compose при подготовке PA4 не выполнялись по просьбе пользователя.
Команды для последующей проверки:

```bash
dotnet build DS-course.sln -c Release
dotnet run --project tests/RankCalculator.Tests -c Release
docker compose config --quiet
```

Для проверки подписчиков дождитесь **двух** строк `Consumer ready` от EventsLogger
с разными `Instance` и именами очередей:

```bash
docker compose logs -f eventslogger
```

Отправьте текст через браузер и найдите его ID в Location ответа POST.
Для одного успешного POST в журнале ожидаются четыре строки:

```text
Event Type=SimilarityCalculated TextId=<id> Similarity=0 Instance=<logger-1>
Event Type=SimilarityCalculated TextId=<id> Similarity=0 Instance=<logger-2>
Event Type=RankCalculated TextId=<id> Rank=0.25 Instance=<logger-1>
Event Type=RankCalculated TextId=<id> Rank=0.25 Instance=<logger-2>
```

Значения в примере соответствуют первому появлению `abc!`; порядок строк может отличаться.
Повторите отправку с разными текстами. Для **каждого** TextId оба логгера должны
вывести **оба** события. Задание при этом выполняет один RankCalculator.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Первый и повторный POST `abc!` | 302; rank `0.25`; similarity `0`, затем `1`; оба события в каждом логгере |
| Пустая форма | Запись существует, rank `0`; оба события в каждом логгере |
| Неизвестный или неверный ID | Запись не найдена |
| Остановка RankCalculator и POST | 302; ожидание rank; SimilarityCalculated в обоих логгерах |
| Запуск RankCalculator | Rank появляется; RankCalculated в обоих логгерах |
| Остановка вычислителя до ack | Повторная доставка; rank прежний; возможны повторные события |
| Перезапуск RabbitMQ | Вычислители и логгеры восстанавливают подписки; дождитесь двух Consumer ready перед новым POST |
| Остановка одного EventsLogger | Второй получает оба события; у перезапущенного логгера новая очередь и нет истории |
| Масштабирование EventsLogger до трёх | После готовности третьей подписки каждый логгер получает оба события |
| Параллельные POST | Каждая успешная отправка создаёт задания и события без одновременных публикаций в одном канале |
| GET и POST между разными Valuator | Antiforgery работает благодаря общим ключам |
| POST при остановленном брокере | 503 с понятной ошибкой, без успешного перенаправления |

Для наблюдения повторной доставки можно включить задержку обработки:

```bash
RANK_DELAY_MS=10000 docker compose up -d --force-recreate rankcalculator
docker compose logs -f rankcalculator
# После строки Processing выполните в другом терминале:
docker compose kill -s SIGKILL rankcalculator
docker compose up -d rankcalculator
```

Последняя команда возвращает обычную скорость, если `RANK_DELAY_MS` не экспортирована.
